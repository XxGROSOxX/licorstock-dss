# Retrospectiva Sprint 1 - Starfish

## Proyecto
LicorStock DSS

## Squad
Tiago Sánchez, Marco Benitez, Andres Araniba, Gerson Salinas

## Objetivo
Analizar el desempeño del Squad durante el Sprint 1, identificando prácticas que funcionaron, problemas encontrados y mejoras concretas para el Sprint 2.

## Tablero Starfish

### Keep Doing
- Usar GitHub Projects para organizar las historias de usuario.
- Mantener backend separado en routes, controllers y services.
- Probar manualmente antes de mover a Done.
- Mantener integración Frontend + Backend + Supabase.

### Less Of
- Menos improvisación al configurar el proyecto.
- Menos cambios grandes sin commits.
- Menos tiempo perdido por errores de rutas y archivos.
- Menos documentación hecha al final.

### More Of
- Más pruebas de endpoints antes de conectar frontend.
- Más revisión de criterios de aceptación.
- Más capturas durante el desarrollo.
- Más comunicación sobre bloqueos técnicos.

### Stop Doing
- Dejar de programar sin verificar el entorno.
- Dejar de cerrar tareas sin evidencia.
- Dejar de dejar archivos vacíos.
- Dejar de mover HU a Done sin revisión.

### Start Doing
- Empezar con checklist técnico del entorno.
- Crear revisión de calidad antes de la demo.
- Hacer revisión cruzada de código.
- Registrar mejoras del proceso como tareas del Sprint 2.

## Acciones de mejora SMART

| Acción | Cómo sabremos que funcionó | Guardián |
|---|---|---|
| Crear y aplicar un checklist técnico antes de iniciar el Sprint 2, verificando Node.js, dependencias, variables `.env`, backend, frontend y conexión con Supabase. | Backend y frontend deben ejecutarse sin errores, y el checklist debe estar marcado como completado en GitHub. | Tiago Sánchez |
| Realizar una revisión de calidad antes de mover historias a Done. Cada historia debe tener criterios de aceptación marcados, evidencia funcional y prueba manual registrada. | Al final del Sprint 2, todas las historias en Done deberán tener evidencia y checklist completado. | Marco Benitez |

## Conclusión
La retrospectiva permitió identificar que el equipo completó funcionalidades importantes, pero también encontró oportunidades de mejora en configuración, documentación y revisión de calidad. Para el Sprint 2 se priorizará trabajar con checklist técnico y validación antes de cerrar historias.
